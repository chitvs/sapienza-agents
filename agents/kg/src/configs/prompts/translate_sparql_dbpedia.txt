SPARQL syntax rules for DBpedia:
- Entities are resources named after their Wikipedia page title: dbr:Albert_Einstein, dbr:The_Matrix. Use the resource identifiers given in the schema context.
- If a resource name contains characters other than letters, digits, underscore, dash or dot (for example parentheses or commas), you MUST write it as a full URI in angle brackets instead of the dbr: short form: <http://dbpedia.org/resource/Mercury_(planet)>.
- Properties come from the ontology vocabulary dbo: (e.g. dbo:birthPlace, dbo:director). Prefer dbo: properties, which are curated and consistently typed.
- Types are asserted with `a` (or rdf:type) against an ontology class: ?x a dbo:Film.
- CRITICAL: DBpedia has NO automatic label service. There is no SERVICE wikibase:label and no ?xLabel magic variable. To return a human-readable name you must either return the resource itself (its URI already contains the name) or bind the label explicitly:
    ?person rdfs:label ?name . FILTER(lang(?name) = "en")
- CRITICAL: The variable you SELECT must be bound in your WHERE clause.
- CRITICAL: When the question asks for an attribute of something reached only after traversing an intermediate entity, that intermediate entity is NOT the answer: keep chaining triple patterns until you reach the variable holding the value the question actually asks for, and SELECT that final variable. See Example 4.
- CRITICAL: Only use the dbo: properties and dbo: classes that appear in the schema context. Do NOT invent property names from your own knowledge: a property that does not exist simply matches nothing and the query returns zero rows.
- Do NOT add a type filter (?x a dbo:Something) on a variable that is already reached through a specific property — it is redundant and, because rdf:type is not matched transitively over subclasses, it often makes a correct query return nothing. Use a type filter only to constrain a variable that would otherwise range freely, as in a superlative.
- For superlatives use ORDER BY + LIMIT 1 rather than a nested SELECT. A subquery is valid as a group pattern `{ SELECT ... }`, but never inside FILTER: there a SELECT is not a valid expression, use EXISTS / NOT EXISTS.
- AGGREGATION: use COUNT with an explicit alias, e.g. SELECT (COUNT(DISTINCT ?film) AS ?count).
- Use OPTIONAL for attributes that may be missing, and LIMIT to bound large result sets.
